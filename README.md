# LLM Radar · 个人大模型决策台

把 **LMArena / Artificial Analysis / llm-stats / LiveBench** 四个评测源按 **6 大类 17 子类**并排，
**不合成总分**，只呈现源内名次与跨源分歧。

它回答的是一个很具体的问题：**这个模型在某件具体的事上排第几，以及不同榜单对这件"事"的看法差多少？**

页面本身零依赖、无构建。`index.html` 用相对路径引用 CSS/JS/数据，双击即可打开，也能直接扔上静态托管。

---

## 一、为什么没有总分

这是本项目最核心的一个决定 —— 不是没做，是刻意不做。

四个源的分数是**四种不同的尺子**：

| 源 | 指标 | 量纲 |
|---|---|---|
| LMArena | Arena Elo | 相对胜负的 Elo（1506 ± 5） |
| Artificial Analysis | Intelligence Index | 自建聚合指数 |
| llm-stats | LLM Stats Score | TrueSkill μ−3σ |
| LiveBench | Overall | 0–100 客观题正确率 |

它们之间**没有任何可验证的换算关系**。任何"平均分"都等于把 Elo 1506 和正确率 73% 直接相加 ——
算式跑得通，但那个数字不指代世界上任何东西。

所以页面上只出现三种量：

| 量 | 含义 | 为什么可以比 |
|---|---|---|
| **名次** | 1 = 该榜第一 | 无量纲，是唯一能跨源并列的量 |
| **原始分** | 各源自己的分数，原样保留 | 只放在 tooltip 与详情表，并标明来源与单位 |
| **跨源分歧度** | 该模型在各源**名次百分位**的极差（0–100） | 全程在"名次"体系内计算，不碰量纲 |

分歧度的分母用**本页展示范围 N**，而不是源站全库规模 —— 用全库会被大盘稀释：
LMArena 文本榜收录 402 个模型，名次 1 与名次 30 的百分位只差 7 个点，分歧度会被压成一条平线。

## 二、快速开始

```bash
git clone https://github.com/Lavie-purple/llm-radar.git
cd llm-radar
```

**只是看页面**：直接双击 `index.html`。数据通过 `data/app.json.js`（而非 `fetch`）加载，
所以 `file://` 协议下也能正常工作，不会触发 CORS。

**想跑数据管道**（重新抓取四个源）：

```bash
python tools/run_all.py              # 全流程
python tools/run_all.py --only aa    # 只跑指定源
python tools/run_all.py --no-snapshot --no-selftest --no-health   # 只抓取与合成
```

**依赖**

- **Python 侧零第三方依赖。** `tools/*.py` 只 import 标准库（`urllib` / `json` / `statistics` /
  `csv` …），不需要 `pip install` 任何东西。开发环境为 Python 3.13。
- **`selftest.js` 只用 Node 内置模块**（`fs` / `path` / `vm`），开箱即跑。
- **`visual_check.js` 是唯一需要装包的**，它跑真实浏览器：
  ```bash
  npm i playwright && npx playwright install chromium
  ```
- 抓取环节要联网；无网络时管道会在抓取步失败并**保留上一版数据**（不会覆盖出空页面）。

## 三、页面怎么读

**两种视图**

- **跨榜名次矩阵** —— 行是模型，列是「源 × 子类」。**每一格是该模型在该榜自己的名次**，
  格内不出现分数，避免把 Elo 和百分比混为一谈。
- **大类详情** —— 按 6 大类展开，每个子类一行，把四个源的原始分并排列出。

**交互**

| 操作 | 效果 |
|---|---|
| 点列头 | 按该列排序；再点切升/降序；第三次恢复默认 |
| 悬停格子 | 原始分、全榜位置、票数/σ/证据局数、来源、覆盖榜数、分歧度 |
| 点击行 | 打开该模型的完整卡片（全维度明细 + 走势） |
| 顶部搜索 | 按模型名 / 厂商过滤 |
| 开源筛选 | 全部 / 开源 / 闭源 |
| 只看覆盖 ≥3 榜 | 过滤掉长尾 |
| 性价比 ÷ 价格 | 名次 × $/1k 对话排序。⚠️ 价格跨度有三个数量级而名次只有一个，结果会明显偏向便宜的小模型，看纯实力时请关掉 |
| 数据变化闪烁 | 相比你上次打开时**档位真的变了**的格子会闪一下 |

**怎么读数字**

- **名次**：1 = 该榜第一。空点 `·` 表示未进本页收录范围或未参评。
- **分歧度**：越高说明该模型越依赖特定评测口径。带「单源」标记的子类只有一个源，
  分歧度无从计算，留空是正常的。
- 每个名次的来源都在列头、tooltip 与详情卡片里写明 —— **不出现无出处的数字**。

## 四、数据源

| 源 | 站内规模（源站自述） | 抓取方式 | 备注 |
|---|---|---|---|
| **LMArena** | 12 榜 / 340 行 | 第三方中文镜像 `arena.atease.dev` 的 RSC payload | 官方无公开 API，这是目前唯一的自动通道 |
| **Artificial Analysis** | 272 模型 | `leaderboards/models` 页面内嵌 RSC payload | 免 API key；官方 API 需付费 key |
| **llm-stats** | 392 模型 / 55 分类 | 站点内嵌数据 | |
| **LiveBench** | 58 模型 / 7 类 | `livebench.ai` + GitHub 原始文件 | release 半年一刷，缺新模型是正常的 |

**当前快照规模** —— 下面的数字全部由 `python tools/stat_app.py` 输出，随数据更新变化：

- 6 大类 / 17 子类（chat 4、general 5、code 2、agent 1、image 2、video 3）
- 每个子类收录前 **30** 名
- **模型库 193 个**，其中开源 42 个、覆盖 ≥3 个榜的 43 个
- 其中 **114 个进入矩阵** —— 入选条件是**覆盖 ≥2 个榜，或在单榜排进前 10**；
  其余 79 个只在「大类详情」视图里按子类出现
- 矩阵 114 × 17 = **1938 格**，有值 379 格、空位 1559 格（**填充率 19.6%**）。
  空位多是正常的 —— 不是每个模型都参加了每一个榜

**单源子类 7 个**（分歧度必然为空）：
图生网页、文生图、图像编辑、文生视频、图生视频、视频编辑，
以及幻觉控制（两个列同属 AA，故亦为单源）。

## 五、数据管道

```
tools/run_all.py
  │
  ├─ 1. 抓取    fetch_lmarena.py / fetch_aa.py / fetch_llmstats.py / fetch_livebench.py
  │             → data/{lmarena,aa,llmstats,livebench}.json
  │
  ├─ 2. 体检    health.py            抓取量对比历史中位数，缩水即失败
  │
  ├─ 3. 合成    build_app.py         四源合并 → data/app.json（+ app.json.js）
  │              └ normalize.py      模型名归一化到 canonical family id
  │
  ├─ 4. 自检    selftest.js          216 条断言
  │
  ├─ 5. 存档    snapshot.py          → snapshots/<时间戳>/
  │
  └─ 6. 走势    build_history.py     扫全部快照重算 → data/history.json（+ .js）
```

**两处设计上的保守**（都是被真实故障教出来的）：

- **抓取器全绿 ≠ 抓全了。** 源站改版最典型的症状恰恰是「HTTP 200 + 解析无异常 + 结果为空」。
  所以第 2 步单独体检：与最近几次的**中位数**比（不用上次值，避免单次抖动误报；趋势性塌缩才该报警），
  缩水即失败。**缩水才是失败，变大只是警告** —— 源站新增一个大类会让行数合法暴涨，
  拿它挡住当天的更新纯属误报。
- **体检不过就不覆盖。** 第 3 步只在「四源全成功 **且** 体检通过」时才重建 `app.json`，
  否则保留上一版可用数据，而不是拿半份数据覆盖出一个看着正常的空页面。

## 七、守卫与自检

改完代码**不要靠看**。这个项目有三层，每一层都能独立抓 bug。

```bash
node tools/selftest.js          # 216 条断言：数据管道 + 前端逻辑（纯内置模块）
node tools/visual_check.js      # 125 项检查：需先起 8758 端口 + 已装 playwright
python tools/falsify.py         # 7 条证伪用例
```

起服务：`python -m http.server 8758 -d .`（`visual_check.js` 会打开真实 Chromium 逐项量 DOM）

**为什么是三层**

1. **`selftest.js`（216 条）** —— 用 DOM 桩把页面逻辑跑起来，覆盖数据管道的每个环节与
   前端渲染分支。**依赖"数据随时间积累"的功能（如走势线）必须在夹具下测**：
   真实数据只有一天时，那条活跃路径根本不会执行，断言看起来"已覆盖"其实是空转。
   它用 `newHarness(historySrc)` 开第二套环境喂合成夹具。

2. **`visual_check.js`（125 项）** —— 起真实浏览器**量 DOM**，而不是看截图。
   量的是：表格列宽是否把内容压成逐字换行、搜索框实际能显示几个字、
   对比度是否过 AA、悬停时色阶是否还保持秩序、悬停是否恰好高亮一行、
   超宽屏两栏是否等高、有无横向溢出。

   > **这个项目里的两个真 bug 都是"看着正常、量出来才现原形"** ——
   > 所以「截图看着没问题」不构成通过依据。

3. **`falsify.py`（7 条）** —— **证伪**：把被守卫保护的那行代码真的拆掉，看守卫是否变红。
   锚点直接绑在源码字符串上，**「锚点失效」和「拆了还全绿」都算失败**（退出码 1），
   防止过期用例长期假装通过。

   > 写这条工具的直接原因：曾有一条守卫**是假的** —— 断言「动画结束后颜色回到档位色」，
   > 但 `animation-fill-mode` 默认 `none`，动画结束后元素本就会回到自身样式，
   > 于是加不加显式 `to` 都能通过。改用 `getKeyframes()` 读隐式终值后，证伪才精确变红。

## 八、改代码前必读

这些都是**实测踩出来的**，不是理论推测。违反任何一条都会引入肉眼看不见的回归。

**硬规则**

1. **不合成任何跨源总分。** 四个源量纲不可换算，只做源内名次与源内百分位。
2. **跨源分歧度的分母是本页展示范围 N**，不是全库规模。
3. **每个名次都要能追溯来源。** 列头、tooltip、卡片都必须写明该值来自哪个源。
4. **成本不跨源换算**，各源各写各的单位（$/M token、$/任务、$/成功任务）。

**已知陷阱**

- **`transition` 在本项目里永不触发，必须用 `@keyframes`。**
  `renderMatrix()` 是 `t.innerHTML = h` 整块替换，1938 个格子节点全部销毁重建；
  `transition` 要求「同一个元素」保存前一个值，新元素只有终值。
  实测：给每个 `td` 打身份标记，重渲染后**带标记的 = 0**；而 `@keyframes` 在 1938 个**新建**节点上全部 `running`。
  技巧：`@keyframes` **只写 `from`、省略 `to`**，隐式 `to` 会取元素自身样式值，省得把六个档位色再抄一遍。

- **热力色在 `.cellbtn` 上，不在 `td` 上。** `td.cell` 的计算背景是 `rgba(0,0,0,0)`。
  要改色阶请改 `.q1–.q6`；给 `td` 铺背景对已有热力色无效，只会让空位 `·` 整块显形。

- **色阶 `alpha` 在深色底上有硬上限约 0.55。** 蓝 `#38bdf8` 合成到 `#14181d`、文字 `#e9eef4`：
  `0.30 → 8.23:1`、`0.55 → 4.54:1`（刚好过 AA）、`0.60 → 4.05:1` 破线。
  想靠拉大跨度换区分度，最多到 0.55。

- **悬停提亮会破坏色阶秩序。** 实测像素反解：静止时 `q1 = 0.292`、`q2 = 0.206`；
  用 `brightness(1.5)` 悬停时 `q1 = 0.419`、`q2 = 0.292` —— **悬停中的 q2 等于静止的 q1**，
  一行内的深浅关系在悬停瞬间失效。且 `filter` 连文字一起提亮（`#e9eef4 × 1.5` 直接截断成纯白）。
  现用 `brightness(1.14)` + 模型列左侧 3px 橙条来定位行，不动颜色。

- **`table.matrix` 是 `width:max-content; min-width:100%`，余量按各列 preferred width 的比例瓜分。**
  容器一旦宽于 `max-content`，余量会按比例灌给所有列，而**模型列 preferred 最大所以独吞大头**
  （实测容器 2080→3400 时模型列 411px→671px，整条死白）。
  给 `td` 写 `max-width` **无效**（auto 布局直接无视，实测仍 708px）。
  矩阵宽度因此被**封顶在 ~2100px**；首列宽度必须由 `--colmodel` 固定，否则余量会全灌进首列。

**开发循环**

```bash
# 改前端逻辑或数据
node tools/selftest.js

# 改样式（先起 8758 端口）
node tools/visual_check.js

# 写完任何守卫后 —— 必须证明它会在被拆时变红
python tools/falsify.py
```

## 九、已知缺口

- **图像 / 视频两个大类只有 LMArena 一个源。** AA 的 image / video Elo 是异步加载的，抓不到；
  llm-stats 的图像/视频榜同为客户端渲染。这两个维度**分歧度全部为空**。
- **单个子类只有一个源时，分歧度无法计算**（当前 17 个子类里有 7 个如此），留空属正常。
- **页面上的名次走势是本站自建的。** LMArena / AA / LiveBench 都只提供「当下快照」，
  走势来自对 `snapshots/` 的逐日重算 —— 所以**只能从本站开始抓取的那天算起，再往前的补不回来**，
  且历史只记各榜前 40 名。当前快照只有 1 天，走势线需 ≥2 天才绘制（页面显示「积累中」）。
- **llm-stats 自带的 14 天名次变化被抓了、但前端没用。** 它提供 `rank_delta_14d`，
  抓取器与 `build_app.py` 已完整保留（落成 `delta14d` 字段，当前数据里 276 处字段、23 处有实际值），
  却**从未被读取**。这是一条现成的、比自建快照更早可用的历史信号，属于尚未开发的缺口。
- **LMArena 数据取自第三方镜像**（`arena.atease.dev`），非官方站。
- **LiveBench release 半年一刷**，最新版里没有当季新模型，缺值正常。
- **同名模型跨源靠规则归一化**，推理强度变体（High / Max / thinking）已合并为同一条并保留最优名次。
  `normalize.py` 的别名表目前为空，**无法归一的模型会保持独立 id**；
  docstring 里提到的 `check_merge.py`（未匹配清单报告）**尚未实现** —— 排查合并问题时需要人工比对。
- **每日计划任务未注册**（Windows `schtasks.exe` 被本机安全策略拦截），
  目前靠手动执行 `tools/run_daily.bat`。
